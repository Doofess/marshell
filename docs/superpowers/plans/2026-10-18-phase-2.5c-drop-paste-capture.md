# Phase 2.5c: File Drop, Image Paste and Screen Capture Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Finish phase 2.5:
- A file dropped on a session's terminal is pasted there as its quoted path.
- A file dropped anywhere else opens in the preview.
- An image pasted with Ctrl+Shift+V into a terminal is saved and its path pasted.
- "Capture screen region" runs the Windows snipping overlay and delivers the capture the same way.

**Architecture:**
- **Core.** A new token-checked route, `POST /v1/sessions/{tab}/paste-paths`, pastes one or more existing absolute paths into a session. Each path goes as its own bracketed paste, separated by a space, with no Enter. The existing attachments and paste routes (2.5b) carry pasted and captured images.
- **Shell (`src-tauri`).** Native drag-drop is turned on, which is the only way WebView2 gives a dropped file's path. A Windows-only `capture_screen_region` command opens `ms-screenclip:` and waits for a new image on the clipboard. WebView2 is allowed to read the clipboard for the app's own origin.
- **Frontend.**
  - The sidebar's row reorder moves from HTML5 drag-and-drop, which native drop turns off on Windows, to pointer events.
  - A `useFileDrop` hook hit-tests the drop point.
  - The terminal catches a paste event that holds only an image before xterm sees it.
  - `LiveApp` delivers all three through one `addImage` path and a new `dropPaths`.

**Tech Stack:**
- Rust core: axum and tokio. Shell: tauri 2.12, tauri-plugin-opener, webview2-com 0.39, plus `windows-sys` 0.61, which is already in the tree through the core, gaining the `Win32_System_DataExchange` feature.
- Frontend: React and TypeScript, and `@tauri-apps/api/webview` (`getCurrentWebview().onDragDropEvent`).
- Tests: `cargo test --workspace`. Vitest runs in the node environment (no DOM), so logic lives in pure modules and components get `renderToStaticMarkup` tests.

**Spec:**
- `docs/PLAN.md` §2.5, around line 856: screenshot and image drop, the delivery rule, multi-CLI, storage, security and exit criteria. "Slice 2.5a decisions" item 5 moved file drop here, and "Slice 2.5b decisions" covers the delivery this reuses.
- `docs/research/attachment-ref.md` for how Claude Code and Codex take a pasted path.
- Research of 2026-10-18, written into `docs/research/drop-paste-capture.md` by Task 6. It has three parts:
  - **Drop.** wry's drop handler reads only `CF_HDROP`, so `drop` means files. The position is physical pixels relative to the webview. Enabling it replaces WebView2's drop handler, so HTML5 drag-and-drop inside the page stops working on Windows (tauri-utils `drag_drop_enabled` doc; tauri#14373).
  - **xterm 6.0.** Ctrl+V sends `^V` and fires no paste event. Ctrl+Shift+V lets the browser fire `paste`, and xterm handles it on its textarea and container. An image-only paste reaches xterm as `paste("")`.
  - **Snipping Tool.** The documented `ms-screenclip://capture…&redirect-uri` needs a packaged MSIX app. Bare `ms-screenclip:` is deprecated but reported working, and it puts the snip on the clipboard. Microsoft says to detect clipboard changes with `AddClipboardFormatListener` rather than poll `GetClipboardSequenceNumber`. WebView2 `navigator.clipboard.read()` needs `CLIPBOARD_READ`, which wry grants only if the builder enabled it.
- The user's answers of 2026-10-18:
  1. Capture uses the OS snipping tool, and the result goes to the clipboard and is then delivered like a region.
  2. An image-only paste through Marshell's paste (Ctrl+Shift+V) is saved and its path pasted. Ctrl+V stays the CLI's own, so Codex keeps attaching clipboard images natively.
  3. A drop on a session's terminal pastes the quoted path or paths. A drop anywhere else opens the file in the preview.
  4. A plain shell's terminal gets the dropped path pasted too, as Windows Terminal does.
  5. Native drop is on, and the sidebar reorder is rewritten with pointer events.

## Global Constraints

- **Dependencies.** No new npm package, and no new crate in `Cargo.lock`. `windows-sys` gains features only. `src-tauri` may depend on `windows-sys = "0.61"` directly, since it is already in the lock.
- **Delivery rule.**
  - Marshell never sends Enter.
  - Paths and references go only through the core's paste routes, which wrap each piece in bracketed paste when the program asked for it (`session.bracketed_paste()`).
  - A paused session is refused with 409 and an ended one with 404.
  - The frontend refuses both before anything is saved, using the 2.5b `deliveryFor` refusal copy: "<name> is paused." and "<name> has ended."
- **Who gets a paste.**
  - **Dropped paths:** every live session, agent or plain shell (answer 4).
  - **A pasted or captured image:** every live session too. It came from a paste or capture the person made in that session, and the clipboard already holds the image, so overwriting it with a path would lose it.
  - **Regions** (2.5b) keep `deliveryFor`: a paste into an agent with a prompt line, otherwise the clipboard.
- **paste-paths limits.**
  - 1 to 32 paths.
  - Each path must be absolute and exist (a file or a folder).
  - No control characters (`char::is_control`) and no `"` (it would break the quoting). The response is 400 with "<path> can't be pasted." or "That path doesn't exist."
  - Each reference is `attachment_ref(agent, path)`, the same per-agent seam as 2.5b.
- **Clipboard read permission.** Only `COREWEBVIEW2_PERMISSION_KIND_CLIPBOARD_READ`, and only for the app's own origins: `http://tauri.localhost`, `tauri://localhost`, and in debug builds the dev server origin from `tauri.conf.json` `build.devUrl`. Every other request is left to WebView2's default.
- **Capture.**
  - The wait for a new clipboard image lasts at most 60 s.
  - It counts only a change that carries an image (registered format `PNG`, `CF_DIB` = 8 or `CF_DIBV5` = 17).
  - It ends early when the frontend cancels.
  - The frontend cancels when the Marshell window has had focus back for 1500 ms with no image, which is what a person pressing Esc in the snipping overlay produces.
  - Non-Windows builds return "Capturing the screen isn't available on this system yet."
- **Image to PNG.** A pasted or captured image that isn't `image/png` is redrawn to PNG through `createImageBitmap` and a canvas. Every image goes through the 2.5b `cropToPng` size loop, so it stays under 20 MB.
- **Copy** (sentence case, plain words):
  - Command: "Capture screen region" (group Tools, binding Ctrl+Shift+X; on macOS it shows as ⌘⇧X but is unavailable).
  - While waiting: "Select a region of the screen. Esc in the snipping tool cancels."
  - Notices:
    - "Added the image to <name>."
    - "Pasted <file> into <name>." or "Pasted 3 paths into <name>."
    - "Opened <file> in the preview."
    - "A folder can't be shown in the preview."
    - "No session to add it to."
    - "Couldn't add the image: <reason>"
    - "Couldn't paste the path: <reason>"
    - "The capture was cancelled."
    - "Capturing the screen isn't available on this system yet."
  - Drop highlight label (shown on the pane under the pointer, `aria-hidden`, since the announcement carries it): "Drop to paste the path into <name>" or "Drop to open in the preview".
- **Accessibility.** Every new path has a keyboard route: quick open for the preview, Ctrl+Shift+V for an image, and the command for capture. Results are announced through the Announcer, with no new live region. The drop highlight is a 2 px dashed outline in the accent colour, and `Highlight` in forced colours. The sidebar reorder keeps Alt+Shift+Up/Down.

## Review Focus

1. **A drag to reorder that goes wrong.** Pressing a row and releasing it without moving, a right-button press, a press on the rename box, and a drag released outside the list must all behave like today's click, menu or no-op. A click must never be swallowed, and a reorder must never fire with no move. Task 2 tests `dragStarted`, `edgeAt` and the click-suppression flag.
2. **A drop on the boundary.** A drop over the splitter, a pane header, an empty pane, the sidebar or the title bar opens the preview. Only a terminal host takes a paste. A drop with the position off by DPI hits the wrong pane. Task 3 tests `dropTarget` with nested elements, and the live check tries 150% scaling.
3. **A paste that has both text and an image** (copied from Word or a browser) must stay a text paste. Only an image-only paste is taken. Task 4 tests `imageOnlyPaste`.
4. **A cancelled or never-starting capture.** The person presses Esc in the overlay, the snipping tool is missing, or text is copied during the wait. Each must end with a clear notice, never a hang, and a text copy must not be taken as the capture. Task 5 tests the pure `clipboardHasImage`-style decision and the frontend's cancel timer.
5. **A dropped path a shell would misread.** Spaces, Unicode, a UNC `\\server\share` path, a folder, or 33 paths. The quoting and the refusals are tested in Task 1.

**Files:**

- Test: `src-tauri/src/capture.rs` `mod tests` (the pure decision), `src/features/capture/capture.test.ts`, `src/lib/keymap.test.ts` (if bindings are listed there)

**Interfaces:**
- Rust:
  - `pub(crate) fn image_arrived(start_seq: u32, now_seq: u32, has_image: bool) -> bool` is `now_seq != start_seq && has_image`.
  - `#[tauri::command] async fn capture_screen_region(app: AppHandle, state: State<CaptureState>) -> Result<bool, String>`:
    1. Read `GetClipboardSequenceNumber`.
    2. Open `ms-screenclip:` with `app.opener().open_url("ms-screenclip:", None::<&str>)`. If that fails, return `Err("The snipping tool didn't open.")`.
    3. Every 150 ms on a tokio interval, check `image_arrived` with `IsClipboardFormatAvailable` for `PNG` (`RegisterClipboardFormatW`), 8 or 17.
    4. Return `Ok(true)` when an image arrives, and `Ok(false)` on cancel or after 60 s.
    5. A second call while one is running returns `Err("A capture is already running.")`.
  - `#[tauri::command] fn cancel_capture(state: State<CaptureState>)`.
  - Non-Windows: `capture_screen_region` returns `Err("Capturing the screen isn't available on this system yet.")`.
  - Polling the sequence number every 150 ms over a 60 s cap is a deliberate choice over `AddClipboardFormatListener`, which needs a message window. Record it as a ruling.
- Permission: in `main.rs`, `add_PermissionRequested` on the `CoreWebView2`. When the kind is `COREWEBVIEW2_PERMISSION_KIND_CLIPBOARD_READ` and the URI's origin is one of the allowed origins, call `SetState(COREWEBVIEW2_PERMISSION_STATE_ALLOW)`. Leave everything else alone.
- Frontend:
  - `captureScreenRegion(): Promise<boolean>` and `cancelCapture(): Promise<void>` wrap `invoke`.
  - `cancelAfterFocus(focusedAt: number, now: number): boolean` is `now - focusedAt >= 1500`.
  - `readClipboardImage(): Promise<Blob | null>` uses `navigator.clipboard.read()` and returns the first `image/*` type.
- Command `capture`: Tools group, label "Capture screen region", binding `{ code: "KeyX" }` (Ctrl+Shift+X):
  1. Announce the "Select a region…" copy.
  2. Start the focus-cancel watcher.
  3. Call `captureScreenRegion()`.
  4. If it returns true, call `readClipboardImage()`, then `addImage(focusedTab, blob)`.
  5. If it returns false, announce "The capture was cancelled."
  6. An error is announced as it is.
  7. With no focused session, it announces "No session to add it to." and doesn't open the snipping tool.

  - TS: `cancelAfterFocus(1000, 2499)` is false and `(1000, 2500)` is true.
  - The keymap has `capture` with KeyX, and no existing binding uses Ctrl+Shift+X. If the keymap's own conflict test covers that, rely on it.
