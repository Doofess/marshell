## Findings

1. **The row's help line sat tight against the profiles list.** The row was a bare fragment above the list, so nothing set it apart. Fixed in `ced45a0f`: the row has its own block with space below (`DefaultFolderRow.css`), with the failing-first test `sits in its own block, so it is set apart from the profiles below`.
2. **A setting changed by anything but the window is overwritten by the window's next save.** The first try at check 7 chose the folder through the core's API while the window was open; the accent change then saved the window's older `default_folder: null` over it. The window reads the settings once and sends every field back with each save, and this holds for every field, not only the new one. Nothing else in the product writes the settings, and the row's own choice goes through the window, so no person can reach it. Once the window had read the chosen folder (a reload), the theme change kept it. Not fixed.
3. **The launcher has "no folder chosen" only while there are no recent folders.** With any recent folder it opens with the newest one chosen and offers no way back to none. So a person meets the default folder in the launcher on a first run (or after the list is empty), and from then on as the recent folder `Marshell`, because a session started in it is recorded like any other. Checks 3 and 4 needed the scratch `projects.json` removed. Not a defect; recorded for slice 6v-2.
4. **Asking the core for the panel's shell before the window has loaded starts it.** A probe of `POST /v1/shell-panel` right after a restart ran before the webview had drawn anything, started the panel's shell in the default folder, and spoiled check 5; that restart was repeated and the window was read first. The route does what it should; a live check reads the panel's header before it asks the core.
5. **A session that falls back to the home folder starts in the real one during a live check.** The core asks the system for the home folder, which doesn't follow the check's `USERPROFILE` (as before this slice). The session in check 8 sat at a prompt there, ran nothing and was closed.
6. The webview's console held one error at every start, `favicon.ico` 404 from the dev server, which is not from this slice.
