## Findings

1. **A refused link or redirect lost its status line at once.** The page reports the end of the cancelled navigation like any other, and that cleared "That address can't be opened in the side pane.". Fixed in `b26362d3`: the line stays until a navigation starts or the address changes (failing-first tests in `pageStore.test.ts`).
2. **Enter in the address box left the keyboard in the box.** Every browser moves it into the page. Changed in `0452089f` (failing-first tests in `BrowserTab.test.tsx`); it stays in the box when the shell refuses the address.
3. **A page unloaded to make room stayed blank when its tab was shown again.** The store still held the closed page, so the tab asked the shell to show a page that no longer existed. Fixed in `7a7653a9` (failing-first tests in `useBrowserPages.test.ts`).
4. **A page that left the screen could be handed the keyboard.** A page keeps its turn at the keyboard while the app borrows it. When a palette command, or anything but a key or a press in the app, took the person to another tab or session, the turn was not ended, and the window coming back to the front gave the keyboard to the hidden page. Fixed in `e86f77d6`: a page that is not on screen never gets it (failing-first tests in `pageFocus.test.ts`), checked live with the window's focus event.
5. **A page hidden while it had the keyboard kept it.** Windows left the focus on the hidden page's window, so typing reached nothing on screen. Fixed in `6ccaf5d4`: when the shell hides a page and the focus is on a window that is not shown, the app's webview takes it. No unit test can hold a window's focus; checked live, where the focus was on the hidden page before and on the app's webview after, for a session switch and a tab switch.
6. **A link to one of the app's own origins leaves an empty tab.** The tab opens, the shell refuses the address, and the tab stays with the status line and no page: the app's webview can't tell its own origins from another loopback address before it asks. The review found the tab was then dead: the store took the refusal for a page, so an address typed there went to a page that didn't exist. Fixed in `d988ec8a` (failing-first tests in `pageStore.test.ts` and `BrowserTab.test.tsx`); in the re-check a Ctrl+click on `http://localhost:1420/` left the tab with the status line, and an address typed there opened with the keyboard in the page.
7. **No session shortcut works from the Address box.** A text box keeps its own keys (`LiveApp.tsx`), so Ctrl+Shift+K does nothing there. Not fixed in the slice: a product question. Changed after the merge (see "After the merge").
8. **A right-click where the app has no menu of its own opens WebView2's menu** (Back, Refresh, Save as, Print, More tools, Inspect in a debug build), on a pane tab for one. It was there before this slice. Not fixed.
9. **Smaller ones, not fixed.** The palette lists the session rows for an unrelated query. A refused typed address puts the page's address back in the box, while a typed path keeps the text. A `file:` link in a Markdown preview is not a link, and a `file:` link or redirect from a page is stopped by WebView2 itself with no status line (the redirect shows its own error page). A tab named "New tab" and the strip's "New tab" button share a name. In a debug build Tauri's refusal names the capability and permission to a page; the release build doesn't.
10. **For the next live check.** A release build started with a scratch `USERPROFILE` that has no `AppData\Local` keeps the app's own webview data beside the exe, and WebView2 then ignores the debugging port. A CDP right-click leaves WebView2's menu open on the desktop until its window is closed. A reload of the app's webview (dev only) forgets which pages are loaded, so pages opened before it stay until the app quits.
11. **A page can't ask to send notifications, and none arrive.** Found in the review, and the first reading of row 11 blamed WebView2. `tauri-plugin-notification` (2.7.0) replaces `window.Notification` in every webview's main frame with its own, whose calls go to the plugin's commands, and Tauri refuses those from a page. So 6q-3 decision 6 (WebView2's own prompt) holds for the camera, the microphone, location and the clipboard, and not for notifications. Not fixed: giving a page the browser's own `Notification` back means a script of ours in every page or a change to how the plugin is loaded, and both are outside what the slice was allowed to touch. Recorded under decision 12 for the user.
12. **A restored tab lost its address when the app closed before its page arrived.** A new page's first report said `about:blank` and not loading, which the app saved as the tab's address and title. Fixed in `d988ec8a` and `cadf6b56`: a blank page that is still loading changes nothing, and a new page starts as loading (failing-first tests in `pageStore.test.ts` and `useBrowserPages.test.ts`; the Rust line has no unit test). Re-checked: a restored tab keeps its address and title through its load, a blank tab ends at rest, and an address nothing answers at keeps its place in the bar.
13. **A page opened under a slot that already had focus didn't take the keyboard.** A Ctrl+click on a terminal address puts focus on the new tab's slot before the shell has made the page. Fixed in `d988ec8a` (failing-first tests in `usePageSlot.test.ts`); re-checked with the windows' focus, which was on the page's window after the click.
14. **A closed session's pages stayed loaded,** with no way to them: the pane keeps a closed session's tabs for a reopen. Found in the review. The first fix unloaded them, and the re-check caught the page of the tab on screen loading again a moment later (a second request in the site's log): the pane draws its last node while it hides, and that tab, as active as it last was, opened the page it had just lost. Fixed in `1eac48f3`: the loaded list counts only the sessions in the list, and a tab asks the store whether it may load (failing-first tests in `useBrowserPages.test.ts`). Re-checked: closing a session with two pages removed both windows (12 to 10) with no new request, and hiding and showing the pane kept its page without a reload.
15. **The request-details drawer was drawn under a page** in a narrow window, where it lies over the pane. Found in the review. Fixed in `1eac48f3`: the drawer covers the page like any overlay, and `coverScan.test.ts` now looks for it. Not re-checked live: it needs a session with a request waiting.
