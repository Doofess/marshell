# S12: Browser pane, a WebView2 child webview (Windows)

Slice 6q-0, run 2026-11-07 on the dev box: Windows 11 Pro 26H2 (build 26300), one 3440×1440 monitor at 100%, WebView2 Runtime 157.0.4341.42, Tauri 2.12.2 with `unstable`, wry 0.57.0, webview2-com 0.39.1.
Build: the never-merged branch `phase-6q-0` under `pnpm tauri dev`, started by `live-check.ps1` with a scratch `MARSHELL_HOME` and CDP on 9333.
Plan: `docs/superpowers/plans/2026-11-07-phase-6q-0-browser-spike.md`. Decisions: `docs/PLAN.md` §9, "Slice 6q decisions (second round)" 2 to 6 and "Slice 6q-0 decisions".

Driver:
- The child webview `spike-page` sits over a placeholder in the preview slot. Rust logs to `<home>/spike-browser.jsonl`, and the loopback test site (`spikes/browser-pane/server.mjs`, port 47620) logs to `site.jsonl` in the scratch folder.
- Keys come from `spikes/browser-pane/keys.ps1` (SendInput, guarded by the foreground window's PID). Until 2026-11-08 it sent a lone key three times: Esc, F5, F12 and Tab went down three times per press, because a chord's modifier list took the key itself twice. 2a's Esc, 2d's F5, 2e's F12 and 3a were rerun with the fix, on a fresh scratch home after a reboot. Chords with a modifier were never affected.
- 4d's bounds were read by a script that asks for per-monitor DPI awareness on its thread. A script started at one scale and still running after a change is handed coordinates scaled to the old one: its first readings at 125% and 150% were off by exactly that ratio, and were dropped.
- The user did Alt+Tab, the edge drags, the Explorer drop and the scale changes by hand.

## Findings

1. **Creating the child takes focus.** `WebviewBuilder::focused` defaults to true. 6q-3's background open (6q decision 6) must pass `.focused(false)`.
2. **Two webviews, one CDP port.** The live check's `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333` reaches every WebView2 environment in the process. The child's profile runs its own browser process, so it can't bind 9333 too, and has no CDP. 6q-3's live checks need the variable scoped to the main webview, or `additional_browser_args` with a second port on the child in dev.
3. **A `ResizeObserver` sees size changes only.** The child followed the placeholder when the status line pushed it down, because its height changed too. A pure move, with no size change, would not be reported. 6q-2 needs a position source as well, such as a layout effect that re-measures whenever the main grid's tracks change.
4. **wry moves focus to the main webview on the window's `WM_SETFOCUS` and `WM_ENTERSIZEMOVE`** (`wry-0.57.0/src/webview2/mod.rs:1325`, the parent subclass only the main webview gets). Expect Alt+Tab back, and the start of a frame drag, to take focus out of the page (tauri#13466). Task 3 checks it.
5. **The app's keymap needs no copy in Rust.** The page's `AcceleratorKeyPressed` handler only decides who owns a key (`route_key`). The app re-dispatches the key as a synthetic `KeyboardEvent`, and the existing keymap acts on it: the palette, the pane toggle and focus mode all worked that way. Ctrl+L and Esc are the two keys the spike handles directly, because they are about the page itself.
6. **A forwarded key ends the page's turn at the keyboard.** The forward moves focus to the app, so a held chord's repeats and the next key land in the app, not the page. When the app is done (the palette closes, the pane shows again), it has to put focus back in the page itself with `MoveFocus`. The spike's key test did, and 6q-3 must decide where that happens.
7. **The find bar is a window of its own.** Ctrl+F's bar is a popup owned by the WebView2 browser process, and it holds the foreground while it is open. Whether Marshell's chords pressed in the find bar reach the handler was not tested. Anything that checks the foreground window's process, such as the key script's guard, sees `msedgewebview2`, not Marshell.
8. **The app's document can't say where in the app the keys go.** With the app in front and the page's `GotFocus` logged, the main webview's `document.hasFocus()` was false, 6 of 6: 3 after Tab into the page and 3 after a click on it. An earlier draft of this finding said true, from a reading whose conditions weren't recorded; this one replaces it. `document.activeElement` still named an app element: the terminal's input, or the "Marshell menu" button. So `hasFocus()` can't tell "the page has the keys" from "Marshell is in the background", and `activeElement` points at the wrong place. Only the child's `GotFocus` and `LostFocus` say where the keys go; the spike relays them as `page-focus` and `page-blur`. 6q-3 keeps that state in the app, and anything that asks "is the terminal focused?" has to ask it too.
9. **Tab off either end of the page arrives as `MoveFocusRequested`**, with the reason Next or Previous. With `Handled(true)` set, WebView2 leaves the focus to the app, and the app puts it on its own element on that side. Tab into the page is the app's own `focus` event on the placeholder, which calls `MoveFocus` with the matching reason, so the page starts at its first or last element.
10. **UI Automation builds the page's tree on first use.** The first `uia.ps1` query after the app started listed only the app's document. Later queries listed both. Whether a screen reader meets the same gap is for the release's NVDA pass.
11. **The freeze is cheap and needs no special cases.** It takes about 45 ms from the overlay opening to the page hidden behind its picture, and the PNG is about 15 KB as a `data:` URL, which the CSP's `img-src` already allows. `CapturePreview` returns the last frame the page drew: the old page during a navigation, and the webview's background before the first one. So a freeze in the middle of a load shows something sensible without any handling. The picture comes in the child's physical size, so `object-fit: fill` doesn't stretch it at 100%; 4d checks 125% and 150%.
12. **A sign-in survives only a clean close.** Chromium writes cookies to disk on a timer and when it shuts down cleanly; the 2 s and 45 s runs in 6c fit a timer of about 30 s. Killed, the app loses what the page stored in the last half minute. Closed cleanly (the controller's `Close`, which `__spike.close()` reaches), one page's six processes exited in 335 ms and kept a cookie set 1 s before. 6q-3 must close every page's webview when Marshell quits, before the process ends. A crash will still lose the last half minute.
13. **The page sees a dark color scheme.** example.com drew its dark scheme, so `prefers-color-scheme` was `dark` in the page. Whether that came from Windows' setting or from the app's window theme was not checked. 6q-3 decides which one pages follow; the profile's `PreferredColorScheme` can set it.
14. **A capability doesn't cover the app's own commands.** Scoping the capability to `"webviews": ["main"]` took the plugin permissions away from every page, but a page at a local origin could still call Marshell's own commands (`spike_log` here). Tauri leaves the app's commands open to every webview at a local origin unless the app lists them in an app manifest (`tauri_build`'s `AppManifest::commands`), which puts them under the capabilities too. Today two things keep a page off them: commands from a remote origin are refused, and the allow-list refuses the app's own origins (`tauri.localhost`, `ipc.localhost`, `tauri://`). In dev, though, `http://localhost:1420` is both local and allowed.

    That gap is the whole local API. Rechecked on 2026-11-08: the pane opened at `http://localhost:1420/spikes/browser-pane/probe.html`, and a script in it called `core_endpoint`. It got the port, the 64-character token and the platform. With that token, it read `/v1/health` and `/v1/sessions`, both 200, so it could have started sessions and typed into them. The same script from the test site's origin was refused: "core_endpoint not allowed. Plugin not found". In a release build the app's origin is `http://tauri.localhost`, which the allow-list refuses (7c), so there the allow-list is the only lock.

    6q-3 should add the app manifest and grant the app's commands to `"webviews": ["main"]` only. The allow-list should also refuse the dev server's origin, so a dev build can't reach the API either. Whether the app manifest works that way was not tried here.
15. **Every page gets the IPC bridge.** `__TAURI_INTERNALS__` was there at both origins and under both capabilities. The ACL decides every call; nothing keeps a page from trying.
16. **Once a page exists, the main window is no longer a "webview window".** Tauri counts a window as one only while every webview on it carries the window's label (`Window::is_webview_window`, `tauri-2.12.2/src/window/mod.rs:1257`). The child breaks that, so from the first page on:
    - `get_webview_window("main")` returns None. The spike's anchor hook found it: it looked the window up that way and never moved the page.
    - A command that takes a `WebviewWindow` argument fails with "current webview is not a WebviewWindow".
    - The window's drag-and-drop events go to the window instead of to the labelled webview (`manager/window.rs:212`). Task 8 checks what that does to `useFileDrop`.

    Marshell looks the window up that way in five places:
    - the taskbar badge (`attention.rs:73`);
    - the taskbar flash (`attention.rs:91`);
    - close to tray (`main.rs:230`);
    - the tray's show (`tray.rs:215`);
    - turning off the browser shortcuts (`main.rs:335`). This one runs at setup, before any page, so it still works.

    So once a page has opened, the first four quietly do nothing. The badge was called over CDP:
    - With a page open, `set_badge` returned "no main window".
    - Once the page closed, the same call worked.

    The worst of the four is the tray's show. Closing the window still hides it to the tray, because that path takes the window from the close event. But the tray then can't bring it back while a page is open. 7b ran it:
    - With a page open, the tray's left click left the window hidden.
    - With the page closed, the same click brought it back.

    A person who closes Marshell to the tray with a page open would have no way back short of quitting.

    6q-3 moves them to `get_window("main")` (`unstable`'s `Manager::get_window`) and keeps the main webview's own calls on `get_webview("main")`. The spike's hooks already take the window from the event or from `get_window`.
17. **At the window's resize event the app's layout is still the old one.** Marshell sizes its main layout from a `ResizeObserver` (`LiveApp`'s `useElementSize` passes `width` and `height` to `MainWindow`). So when the window's `resize` event fires, `innerWidth` is already new, but the pane is still at its old place and width. React draws the new layout a frame later. A report taken at the resize event moved the page to where it already was, and in anchor mode it pulled the page back. The spike now reports from the placeholder's `ResizeObserver` alone. In this layout the pane's width follows the window's (the preview ratio is in `fr`), so every window resize also resizes the pane. A pure move still needs finding 3's position source. Measured on a 120 px resize with `SetWindowPos` (no input):
    - Follow mode moved the page once, 16 to 17 ms after the resize.
    - Anchor mode moved it at 2 ms, with the right edge already in place, and then at 13 ms. The second move fixed the width, because anchoring keeps the old width while the pane's width grows with the window. During those 11 ms the left edge was 60 px off.

    Which looks better during a real drag is 4a and 4b's question.
18. **The opener plugin swallows the page's new-window links.** `tauri-plugin-opener` adds a click script to every webview, pages included (`open_js_links_on_click`, on by default; `tauri-plugin-opener-2.7.2/src/init-iife.js`). It catches every click on a `target=_blank` link, and every Ctrl+ or Shift+click on an http link. It cancels the click and calls `plugin:opener|open_url` instead. From a page the ACL refuses that call, so the click does nothing at all.

    At a local origin the call could go through, and the link would open in the user's browser. That is finding 14's gap again.

    6q-3 builds the opener with `open_js_links_on_click(false)`, as the spike now does. Marshell's own UI loses nothing: it has no `target=_blank` links and opens URLs with `openUrl`. 7b checks that the app's own link still opens.
19. **Each webview hears only its own drops.** Tauri raises a file drag on the webview under the pointer, by that webview's label, and in that webview's own physical pixels (8b). Marshell's `useFileDrop` listens on the main webview alone, so a drop on the page does nothing. The page itself sees no HTML5 drag events and doesn't navigate to the file. A drag that crosses from one webview to the other gives `leave` on the first and `enter` on the second within 1 ms (8a, 8c).

    For 6q-2's "drop a file on the pane", the app hears the page's label too, either through Rust (`on_drag_drop` already sees both) or with a listener on that label. It adds the placeholder's origin to the page's positions, and treats a `leave` followed at once by an `enter` on the other label as one drag, so the drop highlight doesn't flicker at the page's edge. A drop on the pane's bar today goes to the preview (8c); with tabs it should open a tab.
20. **During an edge drag the reports queued up, and the page fell up to 0.9 s behind.** Inside Windows' sizing loop each command's round trip took about 8.6 ms, and the front sent one report per frame, about every 7 ms. The commands run one after another (StrictMode needs that), so up to 121 reports waited and the page trailed the window by 0.4 to 0.9 s. The front now keeps at most one report waiting and measures the placeholder when that report's turn comes; that left a trail of about 17 ms (the user: "less delay trail but still there").

    Predict mode then moved the page from Rust inside the window's own resize, the window message that resizes the window, which runs on the main thread even in the sizing loop. It drew a straight line through the page's last two measured positions. On smooth stretches it was exact (median 0 px), but the layout jumps at three widths: the sidebar folds to the rail below 960 px, and the page takes the whole main area when that is under 720 px (about 772 px with the rail and 971 px with the sidebar open). Across a jump predict missed by up to 441 px, and for a few reports after it by about 20 px, because it had learned a slope from both sides of the jump. In the user's drag, 1 placement in 10 was 99.5 px or more off. The user saw the page "flickers and all jumpy" when the sidebar folded.
21. **Rule mode places the page exactly, jumps included.** MainWindow's layout is arithmetic in `layout.ts` and `previewLayout.ts`: the sidebar's mode and width, the 720 px side-by-side minimum, the drawer, and the divider's ratio in `fr`. The front turns those inputs into straight pieces over the window's width (`paneRule.ts`, 4 pieces for the live check's layout). It sends them ahead of the report whenever an input changes, and Rust places the page from them inside the window's resize (`rules::Rule`).
    - A `SetWindowPos` sweep from 1200 down to 740 px crossed all three jumps: 717 placements, median and 99th percentile 0 px, 2 over 1 px (5.5 px at most, read against a report measured a moment later). The rule never disagreed with the front's measurement.
    - The user's edge drags: 15,791 placements while the window resized, the worst 0.016 px off.
    - Dragging the divider or the sidebar, or the sidebar button, changes the layout with the window still. There the page took the rule sent ahead of a newer report, and 4,220 of 4,537 placements were more than 1 px off. Rust now takes the report itself when it was measured at the window's size now (`rule-measured`), and the rule only for sizes the front hasn't laid out yet. In the user's next divider and sidebar drags, all 6,732 placements were the measured box exactly, set a median 1.7 ms after the front measured it.
    - The page was then a frame ahead of the app: the user saw the URL bar trail it, "less bad" than before. In a change inside the window no window edge moves, so the page can wait for the app's own picture. A report at an unchanged window size is now sent after the app paints the frame it was measured in (one animation frame, then a task; `__spike.setSync(1)`). The user: "url bar now moves without a delay" (637 placements, a median 4 ms after measuring).
    - The rule went ahead of the report as its own command, and the report measured the layout when its turn came, by which time the next rule was often waiting behind it. The check then compared reports with the rule before theirs: 5,278 "misses" in the user's drags, every one matching the layout the report was measured at. 6q-2 sends the rule and the report together.

    So the page is never behind the window's edge, and inside the window it moves with the app's picture. During an edge drag the app's own UI, drawn by its webview a frame or so later, still trails the page: the user saw the URL bar and the window buttons "move with a delay". 6q-0 decision 6 picks rule mode for 6q-2 anyway, and motion for the jumps, with Rust running the app's animation curve.
22. **WebView2 draws a resized webview a frame or more late, the app's as well as the page's.** Until the new picture arrives, the old one stays pinned to the webview's top-left corner. Whatever sits at the right or the bottom jumps, and a strip the old picture doesn't cover flashes. Placement can't fix it, because the window is already in the right place. In the user's drags:
    - The page: its scrollbar flickered and jumped whenever its width changed (the sidebar, the divider, the left border), its right side flickered on left-border drags, and its bottom on top-border drags.
    - The app, with no page open: the terminal text flickered in both shells on any resize, the small shell at the bottom left resized unevenly and its bottom bar jumped, a white strip flashed at the bottom left on bottom-border drags, and the window buttons trailed on left- and right-border drags.

    6q-0 decision 6 makes the app's half a separate slice after 6q. Its leads: the webviews' background colour (the white strip), and the terminal's redraw on resize.

## What 6q-2 and 6q-3 take from this

Draft, written while 3b to 3d, 4a to 4d, 5a's keys, 6b's click, 7b's window controls and 8a to 8c wait for the foreground.

- **Creating the page.** Use `Window::add_child`, with:
  - `.focused(false)` for a background open (finding 1), which the spike didn't pass;
  - the profile at `<MARSHELL_HOME>\browser-profile`;
  - `on_new_window` navigating the pane and then answering `Deny` (6b).

  F12 reached the page's DevTools through the key route, in a dev build (2e). Whether a release build keeps it is 6q-3's call.
- **Browser arguments.** `--disable-features=msWebOOUI,msPdfOOUI` on the child. The live check's `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` is added to these, not used in their place (1c), so the page has no CDP of its own (finding 2).
- **Bounds.** Rule mode (finding 21, 6q-0 decision 6):
  - The front sends its layout as straight pieces over the window's width whenever an input changes, and Rust places the page from them inside the window's resize.
  - A report measured at the window's current size is used as it is, and the front sends it after the app paints that frame, so the page moves with the app's picture.
  - The rule and the report travel in one message, computed together.
  - Keep at most one report waiting (finding 20).
  - Report from the placeholder's `ResizeObserver`, never from the window's `resize` event (finding 17), and watch the layout's inputs too, because a pure move fires no `ResizeObserver` (finding 3).
  - The layout's jumps animate, with Rust running the same curve.
  - The edge inset is 0 (Task 4's ruling).
- **Window lookups.** Every shell call that needs the main window uses `get_window("main")` once pages exist (finding 16): the badge, the flash, close to tray and the tray's show.
- **Key route.** `route_key` as the spike has it:
  - F12 opens DevTools;
  - Esc, Ctrl+L and every Ctrl+Shift chord go to the app;
  - everything else stays in the page, including Ctrl+Alt chords, which AltGr sends.

  The app re-dispatches a forwarded key as a synthetic `KeyboardEvent`, so the keymap has no copy in Rust (finding 5). After a forward, the app puts focus back in the page itself (finding 6).
- **Focus.** The app keeps "the page has the keyboard" from `GotFocus` and `LostFocus` (finding 8). Tab in is `MoveFocus` from the placeholder's `focus` event, and Tab out is `MoveFocusRequested` with `Handled(true)` (finding 9). Alt+Tab and clicks wait for 3b to 3d.
- **Freeze.** `CapturePreview` to PNG, shown as a `data:` image, then the child hidden: 37 to 48 ms in all, thawed in 5 to 11 ms (5a, finding 11). No special case for a navigation or a first load (5c, 5d). The user's verdict on the flash is still to come.
- **Quit.** Close every page's controller before the process ends, or the last half minute of cookies is lost (finding 12).
- **Isolation.** Scope the capability to `"webviews": ["main"]`, and add an app manifest so Marshell's own commands come under it (finding 14). The navigation allow-list stays the other lock (7c).
- **Drop.** Waits for 8a to 8c, and finding 16's note on where the window's drop events go.
